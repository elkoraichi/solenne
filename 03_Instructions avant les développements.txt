# 7. Format des test cases

Chaque test doit avoir un identifiant unique.

Par exemple :

`AUTH-001`

`AUTH-002`

`STAY-001`

`STAY-002`

`EVENT-001`

etc.

Chaque test doit préciser :

### ID

Identifiant unique.

### Objectif

Ce que le test vérifie.

### Préconditions

Ce qui doit être vrai avant le test.

### Données d'entrée

Les données utilisées.

### Étapes

Les actions à effectuer.

### Résultat attendu

Le résultat précis attendu.

### Criticité

* CRITICAL
* HIGH
* MEDIUM
* LOW

### Type

* Unit
* Integration
* E2E
* Security
* Regression

---

# 8. Exemple du niveau de précision attendu

Par exemple, pour le moteur de disponibilité :

### STAY-001 — Demande dans une période libre

**Précondition :**

Maison avec capacité maximale de 10 personnes.

Aucun séjour confirmé.

**Action :**

Un ami demande un séjour pour 4 personnes du 10 au 12 septembre.

**Résultat attendu :**

La demande est acceptée par le moteur comme compatible.

---

### STAY-002 — Capacité dépassée

**Précondition :**

8 personnes occupent déjà la maison.

Capacité maximale : 10.

**Action :**

Un ami demande un séjour pour 4 personnes.

**Résultat attendu :**

La demande est refusée.

Code :

`CAPACITY_EXCEEDED`

Le message utilisateur doit être en français.

---

### STAY-003 — Cohabitation autorisée

**Précondition :**

Un séjour de 4 personnes est confirmé.

Capacité maximale : 10.

**Action :**

Un deuxième ami demande 3 personnes sur les mêmes dates.

**Résultat attendu :**

La demande est compatible.

Occupation totale : 7 / 10.

---

### STAY-004 — Séjour exclusif

**Précondition :**

Un séjour exclusif est confirmé.

**Action :**

Un autre ami demande un séjour sur les mêmes dates.

**Résultat attendu :**

Refus.

---

Ce niveau de précision est attendu pour tous les modules.

# 9. Tests de sécurité

Je veux une section spécifique dédiée à la sécurité.

Ne considère jamais qu'une fonctionnalité est sécurisée simplement parce qu'elle fonctionne normalement.

Pour chaque fonctionnalité sensible, prévois notamment des tests visant à vérifier :

* accès non authentifié ;
* accès avec un compte ami ;
* accès avec un compte administrateur ;
* accès à une donnée appartenant à un autre utilisateur ;
* modification d'une donnée appartenant à quelqu'un d'autre ;
* contournement des permissions côté frontend ;
* appels directs aux Server Actions ;
* manipulation des paramètres ;
* accès à des URLs privées ;
* fuite de données ;
* sessions expirées ;
* comptes désactivés ;
* tokens d'invitation expirés ;
* tokens déjà utilisés ;
* tokens révoqués ;
* tentatives répétées de connexion ;
* récupération de mot de passe.

La sécurité doit être vérifiée **côté serveur**, pas uniquement dans l'interface.

# 16. Gestion des erreurs

Je veux que l'application soit conçue pour **échouer proprement**.

Aucune erreur technique ne doit être exposée directement à l'utilisateur.

L'utilisateur doit recevoir un message clair en français.

Par exemple, ne jamais afficher :

> `PrismaClientKnownRequestError`

mais un message du type :

> "Une erreur est survenue. Votre demande n'a pas été enregistrée. Vous pouvez réessayer."

L'erreur technique doit être enregistrée dans les logs pour permettre son diagnostic.
